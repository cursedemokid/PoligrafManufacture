Password storage now uses PBKDF2-SHA256 with a random 16-byte salt and 600,000 iterations. Plaintext passwords are rejected by the updated login code.

Deployment order: stop all old clients, take a database backup, and run tools/Migrate-Passwords.ps1 with the intended SQL Server connection string. Its default mode reports the number of legacy rows without changes; -Apply expands the Password column to nvarchar(256) and hashes legacy values in a transaction. It does not log credentials. Review and test the script on a copy of the database first. Then deploy all clients sharing that database together. The migration is idempotent for valid hashes; it has not been executed against your database.

Do not run old clients after migration: they cannot verify the new hashes and may write plaintext values. Restore the database backup if rolling back the deployment. Empty/null password accounts require an explicit reset. Existing usernames/passwords remain valid after migration; new and reset passwords are hashed before storage.

This change protects password storage and avoids loading the entire account table during login. A desktop application with direct database access still needs appropriately restricted database permissions; server-side authentication is a separate architectural change.
